# Everyday workflow and interface rules

These Owner decisions apply to tenant and platform interfaces in Arabic and English. Reuse the Laravel/Livewire/Alpine/Tailwind components; use shadcn interaction and layout patterns without adding a second application framework.

## Persistent rules

- Keep purpose, architecture and layout simple: remove redundant taglines and secondary labels rather than explaining a confusing layout. Every change must improve user, developer and agent experience together. Shared controls require hover, pressed, keyboard-focus and disabled states. Forms require adjacent field errors, pending/submission feedback and truthful success/failure feedback. Empty/loading/error states must use the same visual system. Dialog/dropdown/tab motion must be brief, respect reduced motion and never shift the app shell; do not add an animation that delays a routine action. Profile before optimizing; retain measured baseline and resulting timings, and never remove correctness/security caches under a blanket anti-cache rule.

- Navigation must keep the app shell stationary: sidebar width, open groups and its scroll position survive navigation, including bottom links. Settings uses one shared category navigator and the same page-navigation behavior across company settings, Profile, Taxes and Catalogs. Use readable active states, consistent URLs and browser back/new-tab behavior; avoid mixing pane replacement and unrelated full-page layouts. Handle unavailable or malformed preference storage without breaking navigation. Do not animate shell geometry during page initialization.

- Write for a small Palestinian business owner, not an accountant. Arabic should be natural, concise and familiar locally; English must be equally clear. Name the user's action and result. Avoid internal terms such as posting, FEFO allocation, confirmation tokens or allocating credit in routine screens. Explain a real consequence only when it helps a decision; do not repeat instructions beneath obvious fields.
- Sign-in plus an active, explicit platform-operator grant permits control-plane browsing without repeated password confirmation. Sensitive mutations retain their specific confirmation and authorization checks. No compulsory MFA; no expansion of operator grants.
- Default document/activity lists to most recently created first with a stable descending ID tie-breaker, so a newly entered backdated draft remains easy to find. Lookup/select options may use alphabetical ordering. Default table page size is 50 with 100/200 options. Never change economic processing order, payment-allocation order or FEFO to implement display sorting.
- Keep ordinary desktop table/item rows on one line with properly bounded fields and reserved action space. Long text may truncate visually but remains accessible. Validation errors may occupy another line. Mobile uses usable responsive cards rather than unreadably compressed controls.
- Linked record rows open their primary detail page when their noninteractive area is clicked. Buttons, links, selection, modifier keys and editable cells retain their own behavior. Keep real keyboard-accessible links.
- Expose common permitted actions directly: open, edit, confirm eligible drafts, receive/pay money and PDF. Use clear consistent icons (banknote for payment; PDF-labelled document for PDF), accessible names and tooltips. Never make an immutable financial operation an unguarded click or permit posted-history deletion.
- Use compact desktop buttons and at least 44px touch targets. Put related actions inside/beside their field: camera in barcode input, full balance in amount input, new customer/supplier beside selector, new product beside product search. Increase/remove-line symbols must remain legible. Use restrained green plus/red minus with readable contrast.
- Create forms start with essential fields. Edit forms show all existing customer/supplier details by default. Optional create sections with multiple fields use an accessible switch. Show small optional fields directly; do not hide a single field behind an extra click. Use aligned responsive grids and available page width, avoiding unnecessary nested cards and wasted space.
- Show the compact warehouse/currency/due-date row directly. Hide exchange rate when the transaction uses company base currency; keep its canonical value exactly one and revalidate on the server. Show rate controls only for real currency conversion.
- New document language inherits the current interface language, subject to company-enabled languages. Printing defaults to that interface language. Editing existing drafts must preserve stored intent unless the user changes it. Product-image inclusion is an accessible main-form toggle.
- Non-destructive quick-create dialogs close with outside/backdrop click, Escape or Close; return focus to their trigger and preserve the parent draft. Internal clicks never dismiss. Prevent dismissal during an ambiguous in-flight save. Destructive/irreversible operations keep appropriate explicit confirmation.
- Money is displayed and entered with two decimal places. Unit-count quantities use whole numbers. Do not silently round existing fractional stock, exact valuation, FX, unit conversion or immutable history: investigate any conflict with supported fractional units before changing those contracts. Storage/arithmetic remain exact decimal strings.
- Quantity buttons react immediately in browser draft state and coalesce server synchronization; do not perform a database write per tap. Flush pending edits before save, validation or confirm; keep retry/conflict/offline protection. Browser-calculated totals are previews; server authorization, exact arithmetic and canonical posting remain authoritative.
- New activity dates default to today in the company timezone; preserve stored edit dates, payment terms and genuine expiry/period semantics. A payment launched from an invoice inherits its currency and a matching eligible account; standalone payments prefer an eligible company-base-currency account. Never guess foreign settlement rates from historical invoice rates. The user enters received amount; remaining balance/allocation totals update clearly. Hide irrelevant conversion/advanced controls. Explain customer credit as money already received and not yet used, rather than accounting jargon.
- Treat slow navigation as a defect to measure. Separate HTTP/PHP/bootstrap, SQL, Livewire round trips and browser rendering. Compare repeated equivalent reads at low concurrency. Do not weaken tenant/security/commit checks or invent caches/indexes without evidence.
- Product search uses an icon-only camera action INSIDE the search input group, with a localized accessible name. Product detail sections use keyboard-accessible tabs with immediate switching of already-authorized content and lazy loading only where needed.
- Arabic tables retain logical RTL alignment; document numbers, dates, barcodes and currency amounts use isolated LTR runs (`bdi`/`dir=ltr`) without reversing the entire row. Apply this to headers, cells, inline controls and related payment tables. PDF filenames derive from the human document number, sanitized for safe filenames; drafts use a clear stable fallback.
- A confirm action should need only one deliberate user confirmation. Do not stack browser `confirm()` with another review page. Canonical preview/validation/token/idempotency checks may run internally, but cannot be skipped or reimplemented in the browser. When validation fails, explain the specific recoverable field instead of a generic list of accounting concepts.
- Zero price/cost is a valid business input where supported by the canonical domain; give a restrained warning when useful rather than blocking merely for zero. Negative values, invalid units, missing lot quantities or unbalanced accounting are different errors and remain protected. Default to the company's valid default/sole warehouse; never select a foreign/inactive warehouse or fabricate expiry/valuation.
- Sharing uses one compact reusable dialog: create/copy link and a clear expiration/access choice only when relevant. Preserve existing password, revocation and public-data boundaries without overwhelming routine use.
- Document headers prominently show total, paid and remaining in consistent restrained summary cards, with due date where relevant. Calculate through canonical read models, including posted returns, reversals, credits and allocations; never equate an invoice total with cash received.
- Dashboard presents a small set of useful, permission-scoped figures: net confirmed sales/purchases for the selected period and actual balances by cash/bank/check nature. Distinguish revenue, collections and outstanding balances. Never add different currencies or financial instruments together without the existing exact conversion/domain rules. Inventory starts with a searchable/filterable list of products, locations and available quantities; advanced lot/cost operations remain accessible under proper permissions.
- Invoice/purchase row payment shortcuts should open a compact contextual payment dialog reusing the canonical full-page form/save path. Provide a working full-page fallback. Preserve unsaved parent state and double-submit/idempotency protection; never create a second financial writer.
- Keep public Hostinger files manifest-only and source-map-free, replace builds atomically, preserve the configured root and verified off-host recovery. Remove only verified disposable staging. Preserve private files, translations, unique source and financial history.

## Navigation workload rule

- Treat ordinary page navigation as a small authorized read. Do not lock company rows repeatedly to enumerate UI options. Use a finite fresh permission snapshot for presentation; reauthorize independently at canonical execution and delivery. Do not cache grants or tenant data across requests.
- Closed assistant/dialog controls must not resolve record details or enumerate panel/report choices until opened. Keep the launcher's permission and policy visibility checks. No provider request may result from ordinary navigation.
- Serve the established IBM Plex webfonts from the versioned first-party build, with their full original license. Avoid an external render-blocking font stylesheet on tenant, platform and sign-in pages. Keep swap rendering, hashed caching, atomic manifest replacement and no source maps.
- Distinguish cold template/bytecode work from warm rendering and SQL. Blade precompilation and web bytecode warming are separate; verify the important entry routes in the web runtime before release. Do not declare all slowness solved from a warm list request or introduce SPA caching that can replay stale tenant/permission state without an independent design review.
- The 3 November follow-up reproduced 37 queries and row locks in intent enumeration; the corrected disposable regression records 3 read queries, with fresh membership/policy/permission revocation checks. Granular local render observations measured invoice and Settings cold views at roughly 1.2/1.8 seconds, versus 6/12 ms for the same cached templates. These are bounded observations, not a universal latency guarantee.

## BoardUI reference and actionable validation

- BoardUI's official agent skill is installed user-wide in `~/.agents/skills/boardui` (verified 3 November 2026 with pinned CLI 0.5.9; telemetry disabled). Consult its official component, table, sidebar, dashboard, overlay and RTL guidance alongside shadcn. This application remains Laravel/Livewire/Alpine: React-only components are not drop-in replacements and must not introduce a second runtime incidentally. No Pro activation or paid calls.
- A Confirm button must reach its actual server action through the shared operation queue after pending quantity edits. Verify the real browser-to-server path, not only a direct PHP method call. Never present a blocked submission as a successful no-op.
- Blocking issues use brief localized language, an inline message at the affected field/item, an accessible summary and focus on the first visible invalid control. Preserve the draft; never bypass stock, credit, permissions or canonical posting rules.
- Reading direction and column alignment are distinct. LTR document numbers, dates and amounts must still align with their Arabic table headings. Verify actual computed alignment and visual output in both locales, including payment/history tables.

## Restrained hierarchy, typography and legibility

- Establish a readable baseline across all tenant, platform and settings interfaces: 14px (`text-sm`) for tables, navigation links, buttons and interactive controls; 15–16px (`text-base` or `text-sm sm:text-base`) for prose and form inputs to prevent browser viewport auto-zoom on mobile; 12–13px (`text-xs`) strictly reserved for genuinely secondary metadata, badges, timestamps and helper captions.
- Eliminate micro-type (`text-[9px]`, `text-[10px]`, `text-[11px]`); never shrink text to force a broken grid or cramped table to fit. Arabic typography requires appropriate line-height (`leading-normal` or `leading-relaxed`) and adequate horizontal width.
- Main desktop navigation and icon rail follow the 264px expanded / 76px collapsed standard (referencing `Ramallah Navigator` commit `6a2ef244`): clear active states, bounded scrolling, consistent 18px icons (`w-4.5 h-4.5`), 14px labels (`text-sm font-semibold`), sticky footer with directional collapse toggle, and accessible hover/focus titles on collapsed rails. Every permitted destination must be reachable without duplication across groups.
- Settings navigation follows Linear/Apple Notes restraint: a single editable pane per active section (`/settings` defaults directly to editable Company Identity), direct category navigation, and retirement of redundant overview walls, promotional essays and duplicate future-feature notices.
- Document and print simulator layout uses invariant physical positioning (`left: 0; top: 0; transform-origin: 0 0;`) regardless of document reading direction (`dir="rtl"` / `dir="ltr"`), ensuring the scaled A4 sheet fits inside the preview viewport in Arabic and English without horizontal offset or blank paper regressions.
- Traceability and verification truth: in registers and handback documentation, `implemented`, `tested`, `visually checked` and `Owner acceptance` are strictly separate statuses. Test execution proves functional assertions, browser inspection verifies visual geometry and parity, and Owner review remains the sole authority for acceptance.

## Embedded payments and mobile final actions

- Invoice payment defaults apply inside invoice creation as well as standalone/contextual receipt forms: current company-local receipt date, an eligible account matching invoice currency where available, base-currency rate exactly one, and full received amount tracking the invoice total until deliberately edited. Preserve manual selections/dates; clear amounts when their currency changes. Require explicit foreign settlement rates. Same-currency partial payments need one amount; show separate applied amounts only for actual conversion.
- Mobile document bars expose both Save Draft and the existing permitted Confirm action, using the shared document operation queue to flush pending edits and block duplicate/uncertain submissions. Invoice/purchase toolbars share the responsive component; purchase returns reuse their canonical posting service. Quotations retain Save Draft because they have no posting action.
