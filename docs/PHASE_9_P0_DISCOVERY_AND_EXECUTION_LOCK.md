## 8. Statement, receipt and quotation issuance policy

**C5 — accepted fixed issuance data:** new Customer Statement shares store validated `from`, `to/as_of`, currency scope, Company timezone, issue instant/locale and the safe canonical financial DTO, including issuance party/company identity and exact opening/rows/closing. Freeze it at authorized creation under consistent read from the canonical query. Backdated postings/master renames later do not rewrite it. New private statements intentionally produce a new read; neither path introduces another calculator.

Store a versioned allowlisted canonical JSON DTO, not a serialized model. Define deterministic UTF-8 encoding, recursively ordered object keys, deterministic statement-entry ordering, exact decimal strings and explicit currency/unit fields; reject unknown fields/versions and floats. SHA-256 is computed over the canonical plaintext bytes, stored with the version, and verified after authenticated decryption and schema validation before delivery. Never silently normalize financial content into a different revision.

Use Laravel authenticated encryption and private `MEDIUMTEXT` storage (or equivalent bounded private blob). Proposed hard issuance caps: **2 MiB plaintext**, **4 MiB actual stored ciphertext bytes** including encryption/base64 envelope, and **1,000 statement entries** before unbounded hydration. These and §13 render budgets are acceptance targets requiring measured AR/EN/multicurrency validation, not guaranteed Hostinger limits. Ordinary `TEXT` is insufficient; SQL strict mode must reject rather than truncate. Reject over-cap, malformed or encryption/round-trip verification failure before granting any active token; do not truncate entries or partially issue a statement.

Issuance atomically commits share, successfully encrypted snapshot, version/hash/scope and Company-scoped unique request key. Return a usable token only after successful commit. Idempotency compares the normalized authorized issuance payload (subject, validated scope, locale, access policy and revision) as well as request key; preserve the captured snapshot/hash on exact retries, rather than rerunning today's query. Changed intent with the same key conflicts. Serialize competing issuance attempts, recheck source/Company/actor before commit, and roll back snapshot/share/audit issuance metadata together on any failure. No committed active grant may lack its verified snapshot. Reads fail closed on missing key, decryption, schema or integrity failure; **no fallback to live recomputation**. Key-loss failures make existing content unavailable until secure recovery, never authorize a replacement payload.

Key rotation/recovery: Laravel `APP_PREVIOUS_KEYS` retains the prior decrypting keys needed by live snapshots and encrypted token recovery while new writes use the current `APP_KEY`. Retention must cover outstanding grants and the encrypted-backup recovery window; do not retire a key until recoverability is verified or affected grants are explicitly retired. Keep key custody/version inventory securely separate from encrypted database/private-file backups. On a disposable restore, restore matching configuration/keys from authorized custody, verify decryption/schema/hash and current access policy, then authorize recovery; never log keys, tokens, passwords or complete DTOs. Rotation/recovery tests belong to P9-C; application-wide restoration rehearsal remains Phase 10. No key/configuration/backup changes are performed in this PR.

Legacy statement shares with null profile remain clearly labelled **live full-account statements**, using their actual historical behavior; no fabricated original snapshot or silent narrowing. Management must offer explicit revoke/reissue as a fixed statement. Changing password/expiry cannot silently replace financial payload; regenerate a new share for a changed range. A frozen issued statement may intentionally precede later reversals; show issue/as-of labels and check share/Company/source eligibility, not today's open balance. Source retirement denies access without rewriting the issued content.

New quotation shares bind the issued revision's economic/identity fingerprint. Draft transition denies access; resend with changed payload requires explicit reissue, rather than letting the old link silently expose revised terms. Existing legacy quotation grants cannot be assigned their unknown original revision retroactively. Preserve token identity and label legacy semantics; management can explicitly revoke/reissue. Do not rewrite quotations or posting snapshots to implement this policy.

**C2 — receipt disclosure frozen at issuance:** a new public Customer Receipt share discloses only the immutable receipt's issued financial facts, its original allocation legs and their corresponding exact receipt-currency, invoice-currency and base settlement values. Persist an allowlisted issuance disclosure profile/fingerprint identifying those original legs and frozen public facts; do not obtain public scope from a later expanded private receipt DTO. Later payment applications, invoice associations and application-event rows are excluded even if already visible in the authenticated private view. Later application to another invoice must never expand the original token's HTML/PDF/print/API scope. The private receipt may show later applications in a clearly separate labelled section. A disclosure change requires fresh authorized preview and reissue, rather than mutating the old token; offer explicit revocation of the old grant. Reversal/void/source retirement denies future public delivery, including an already unlocked session. Do not infer historical FX or settlement values from current configuration.

These accepted policies add read-output provenance only; they do not claim snapshots already exist. Historical shared invoice/return/receipt values use canonical stored sources and explicit current validity (void/reversal denies); financial DTO construction never falls back to current masters. No canonical payment writer or allocation/application event is changed.

## 9. Catalog data and price policy

Hide inactive/deleted Products in public content; administration retains their selected history for correction. Eligibility checks cannot rewrite approved text, image identity or price disclosure.
