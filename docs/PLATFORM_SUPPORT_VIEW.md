# Platform support view

This separately authorized feature lets an explicitly permitted platform operator inspect one active company's workspace as its active Owner. It is **read-only support impersonation**, not a target login, financial delegation, stock importer credential or an override of tenant policy.

The operator needs the new explicit `company.support` grant and must submit their own current password and a short reason at start. Existing production grants are not expanded by deployment. MFA remains optional under the existing policy. A support session lasts at most 15 minutes; it binds the real operator, target company/Owner, grant revision and server-side session. Every request rechecks the real platform identity, current credential proof, active grant, target membership and company status. Revoke/regrant, password changes, expiry and loss of target ownership end access. Impersonating an active platform operator or nesting support sessions is refused.

The authenticated session and remember identity remain the **real operator**. Only the request-local user and CompanyContext are replaced for eligible tenant reads, then restored/cleared in `finally`. Company selection and target login/preferences/password/MFA/recovery data remain unchanged. Session IDs rotate on entry and exit. The AR/EN banner identifies the real operator and viewed Owner, shows the deadline and provides an always-available POST exit. Locale changes affect the support session only. AI is disabled for the support request without changing either company's policy.

All mutating HTTP/Livewire/API submissions, account/profile/security, tenant switching, backup/export and platform operations are blocked while support view is active. Editing controls are disabled for clear feedback; server authorization does not depend on disabled controls. `TenantWriteAccess` refuses business writers even when subscription enforcement is OFF. A request-local SQL backstop also refuses raw mutation attempts from legacy GET handlers. Only the reviewed tenant workspace GET routes and checksum-verified product-index search/filter/pagination/barcode-read requests are eligible. No other component, arbitrary property or mutation method can use this exception, and existing target permissions/scopes continue to redact and constrain data. Unsupported interactive controls require ending support and following the customer's normal authorized workflow. No financial action may be attributed to the target through support view.

Existing append-only platform audit events record `support.started` and `support.ended` with the actual operator, target company/Owner, reason and an independent correlation reference. No password, authentication session identifier, recovery code or credential is logged. Start fails if its audit cannot persist. Exit always removes support authority even if storage fails, with a minimal operator log warning. Existing operator audit views show support context on desktop/mobile. No new database table, migration, infrastructure or impersonation package is required.

The session/audit decisions follow [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) and [logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html), implemented using the application's existing Laravel guards, platform proof, tenant context and audit boundary. These references inform the design; they do not certify the implementation.

This feature cannot resolve an opening-stock import's missing actual tenant operator. Creating financial/stock history still requires the existing canonical authorization and a separately approved, truthful execution workflow. Do not enable write-capable impersonation or add a financial bypass under the guise of support access.

Acceptance requires focused HTTP/domain/security tests, proof of tenant isolation and unchanged target credentials/preferences, AR/EN desktop/tablet/mobile browser checks, dependency/build checks and a complete source-pinned QA gate for the integrated release. Source publication does not activate grants or authorize customer data changes.
