# Mobile V2 offline cash sale pilot

The backend requires `MOBILE_V2_OFFLINE_SALES_ENABLED`, the existing mobile/merchant/V2/cash flags, and the company's enabled cash-only offline policy. Duration, count and total must be configured explicitly in `company_mobile_settings`. V1 bootstrap continues to report offline unavailable. The V2 operations below require native bearer authentication and current invoice and cash receipt permissions for the selected company.

## Wire contract

- `POST /api/mobile/v2/companies/{companyId}/offline-sale-lease` accepts exactly `{"catalog_snapshot_version":"<version from the cached catalog>"}`. It returns public company/actor/device IDs, `lease_id`, `catalog_snapshot_version`, UTC `issued_at` and `expires_at`, currency and minor units, configured warehouse/cash account/walk-in customer/tax identifiers, the three policy limits, and posted count and total. A request for the same active lease returns that lease and its current counters. A request with a different snapshot or policy receives a conflict until the lease expires.
- `POST /api/mobile/v2/companies/{companyId}/offline-events` uses the existing Revision 3 `offline-sale-intake-request` and `offline-sale-intake-response` schemas. Hash the complete event using the existing restricted JCS serializer. Keep the digest, case, decimal lexemes, line order and event ID from the saved outbox entry. The envelope must agree exactly with its event. HTTP 200 means the official invoice and payment were committed or recovered after a lost response.
- `GET /api/mobile/v2/companies/{companyId}/offline-events/{clientEventId}/status` uses the existing `sale-event-status-response` schema. Verify the returned digest before adopting the official receipt. `unknown` means this endpoint found no committed receipt. Preserve the saved event for retry or review. A matching committed receipt can be recovered after lease expiry by the same authorized staff and device.
- HTTP 409 uses the V2 error envelope and `error.conflict_evidence.reason` for recognized conflicts. Treat expired/stale/over-limit/unsupported events as requiring explicit recovery. Preserve the original bytes. A refusal rolls back the lease charge and financial effects. The server records successful admissions. Owner-assisted recovery of rejected cash already collected still needs a paired workflow.

## Scope of this candidate

One active lease per company, staff member and device. First submission and the client-declared capture time must fall within the server lease window. Future client timestamps are refused. The client timestamp is an unverified audit field. The canonical invoice and payment use the server's posting business date. Renewal cadence, elapsed capture grace, clock skew, posting-date treatment, multi-device exposure and numeric limits need business approval before activation.

This candidate uses the configured warehouse, cash account and default tax choice, including an explicitly configured no-tax setup. It supports full cash in the company base currency at its authoritative precision. Current product/unit price, unit, tax and warehouse stock are rechecked at admission. The lease binds a server-verified catalog version at issuance. Live stock determines fulfillment for each queued sale. The catalog version remains valid for the lease window. Stock remains available to other writers until canonical posting. Android needs warehouse-specific availability or an explicit unconfirmed-stock display, and must reconcile rejected sales where stock has changed.

Android needs to persist lease scope, the catalog version, limits, exact pending amounts and the complete immutable event together with the local receipt. Offline capture needs matching catalog pages and cash/tax context, no over-budget capture, persisted expiry and pending counts across restart, and server status recovery before any resend after an uncertain response. Qualify exact tax, units and totals against Laravel before collecting offline cash. Use two decimals for money entry and display, and preserve authoritative wire and storage precision. If the checkout cannot collect the exact settlement under that input rule, require a qualified recovery path before collecting money.

## Required authority witnesses on the combined head

Use separate MariaDB transactions with an observed held lock, contender connection and blocked statement, then explicit release. Exercise both winner orders for login candidate selection versus membership/company deactivation, device and token revocation versus admission, production Fortify password reset versus admission, MFA enable/disable and single-use recovery-code issuance versus lease/intake, and role/direct permission removal versus issuance, intake, replay and status. After an authority mutation wins, assert no new financial or lease effects. When canonical posting wins, assert one event receipt and all financial legs before later access is denied. Exercise same-ID replay and two distinct events competing for the final lease slot. Include the AI owner path's membership → policy → principal locks and support write path's company → operator grant → operator principal → owner memberships, with overlapping principals. Run these witnesses again against the exact combined head before accepting PR #95 authority.
